# Pattaya Smart Tourism Dashboard

ระบบต้นแบบคลังข้อมูลและแดชบอร์ดวิเคราะห์พฤติกรรมนักท่องเที่ยวเมืองพัทยา **ทุกตัวเลขบนแดชบอร์ดมาจากข้อมูลจริงที่นำเข้าแล้ว ไม่มีข้อมูลจำลอง**

ข้อมูลเก็บอยู่บน **Supabase (PostgreSQL)**

## เริ่มต้นใช้งาน

1. สร้างไฟล์ `.env` ที่รากโปรเจกต์ (ข้าง `README.md`) ใส่บรรทัดเดียว:
   ```
   DATABASE_URL=postgresql://postgres.<project-ref>:<รหัสผ่าน>@aws-0-<region>.pooler.supabase.com:5432/postgres
   ```
   หาได้จาก Supabase → ปุ่ม **Connect** → **Direct** → Method **Session pooler**
   - ลบวงเล็บ `[ ]` รอบรหัสผ่านออก
   - ถ้ารหัสผ่านมีอักขระพิเศษ ต้องเข้ารหัสแบบ URL เช่น `@` → `%40`, `#` → `%23`, `/` → `%2F`
   - ไฟล์นี้อยู่ใน `.gitignore` และ `.dockerignore` แล้ว ห้าม commit

2. ติดตั้งและรัน
   ```powershell
   python -m venv .venv
   .\.venv\Scripts\Activate.ps1
   pip install -r requirements.txt
   python -m uvicorn app.main:app --reload
   ```

เปิด `http://127.0.0.1:8000` ในเบราว์เซอร์ ตอนเซิร์ฟเวอร์เริ่มทำงานจะสร้างตารางบน Supabase ให้เองถ้ายังไม่มี

> สคริปต์นำเข้าพิมพ์ผลเป็นภาษาไทย ถ้า PowerShell แสดง `UnicodeEncodeError` ให้ตั้ง `$env:PYTHONIOENCODING="utf-8"` ก่อนรัน

## ฐานข้อมูล Supabase

- แอปต่อ PostgreSQL ของ Supabase โดยตรงด้วย `psycopg` ผ่าน connection pool ([app/database.py](app/database.py)) ไม่ได้ใช้ REST API หรือ anon key
- **เปิด Row Level Security ทุกตารางโดยไม่มี policy** จึงไม่มีใครอ่าน/แก้ข้อมูลผ่าน REST API ของ Supabase ได้ แอปต่อด้วยสิทธิ์เจ้าของตารางซึ่งไม่ถูก RLS บังคับ จึงใช้งานได้ตามปกติ
- เวลานำเข้า (`imported_at`) เก็บเป็น `TIMESTAMPTZ` และแสดงบนแดชบอร์ดเป็นเวลาไทย
- Supabase แบบฟรีจะหยุดโปรเจกต์อัตโนมัติถ้าไม่มีการใช้งาน 7 วัน ถ้าเซิร์ฟเวอร์ต่อฐานข้อมูลไม่ได้ ให้เข้าไปกด Restore ที่หน้าโปรเจกต์

### ย้ายข้อมูลจาก SQLite เดิม

ก่อนย้ายไป Supabase ระบบเก็บข้อมูลในไฟล์ `pattaya_tourism.db` (SQLite) ไฟล์นี้ยังเก็บไว้เป็นข้อมูลสำรอง
คัดลอกขึ้น Supabase ได้ด้วยคำสั่งเดียว โดยเก็บ id เดิมทุกแถวและตรวจว่าจำนวนแถวตรงกันก่อน commit

```powershell
& .\.venv\Scripts\python.exe scripts\migrate_sqlite_to_supabase.py            # Supabase ต้องยังว่าง
& .\.venv\Scripts\python.exe scripts\migrate_sqlite_to_supabase.py --replace  # ลบของเดิมบน Supabase แล้วคัดลอกใหม่
```

| `GET /api/air-quality` | PM2.5 เฉลี่ยรายเดือน และจำนวนวันที่เกินมาตรฐาน |

## การนำเข้าข้อมูลใหม่

### นำเข้าผ่านหน้าเว็บ

ผู้ดูแลระบบนำเข้าไฟล์ได้จากเมนู **จัดการข้อมูล** โดยไม่ต้องใช้ command line รองรับ `.csv` ของเมืองพัทยา
(นักท่องเที่ยวรายเดือน ประชากรแฝง ปริมาณรถรายแยก ผู้โดยสารเรือ PM2.5 ขยะเกาะล้าน รายได้ของเมือง ระบบเลือกรูปแบบจากหัวคอลัมน์เอง) และรายงาน `.xlsx` ขนาดไม่เกิน 10 MB

- **ใช้ไฟล์ "รวมสถิติ" ของแต่ละชุด** ไฟล์รายปีบางไฟล์ของต้นทางมีข้อมูลเพี้ยน เช่น ไฟล์ผู้โดยสารเรือปี 2567 มีปีไล่ไปถึง 2571 (ระบบจะปฏิเสธปีที่ยังมาไม่ถึง) และไฟล์ขยะเกาะล้าน "ปี 2568" มีเนื้อหาเดียวกับปี 2567
- ชุดขยะทั้งเมือง (150) ใช้หัวคอลัมน์เดียวกับชุดขยะเกาะล้าน ระบบจะปฏิเสธเพราะมีประเภทขยะที่ไม่มีบนเกาะ
- **ไฟล์หนึ่งเข้าทั้งไฟล์หรือไม่เข้าเลย** ถ้ามีแถวผิด (ตัวเลขอ่านไม่ได้ เดือนไม่ใช่ 1–12 ปีไม่ใช่ พ.ศ.) ระบบจะบอกเลขบรรทัดที่ผิดและไม่แตะข้อมูลเดิม
- **นำเข้าไฟล์ชื่อเดิมซ้ำ = แทนที่ข้อมูลของไฟล์นั้น** ส่วนไฟล์ชื่อใหม่ที่มีช่วงเวลาซ้ำกับไฟล์เก่า จะแทนที่เฉพาะช่วงที่ซ้ำ เพื่อไม่ให้ยอดรวมนับเดือนเดียวกันสองรอบ (สคริปต์ `import_csv.py` ทำแบบเดียวกัน)
- นำเข้าปริมาณรถซ้ำแล้วพิกัดของแยกที่เคยหาไว้ยังอยู่ แยกใหม่ที่ยังไม่มีพิกัดต้องรัน `scripts/geocode_intersections.py`
- ไฟล์ที่นำเข้าไม่สำเร็จถูกบันทึกในประวัติการนำเข้า แต่ไม่ขึ้นเป็นแหล่งข้อมูลบนแดชบอร์ด

### อัปเดตอัตโนมัติ

ชุดข้อมูลที่มาจาก API ภายนอกอัปเดตเองตามรอบ โดยดูจากเวลานำเข้าล่าสุดในตาราง `imports`

| ชุดข้อมูล | รอบ |
|---|---|
| สภาพอากาศรายวันย้อนหลัง (Open-Meteo Archive) | ทุกวัน |
| วันหยุดและเทศกาล (ปฏิทินวันหยุดไทย) | ทุก 7 วัน |
| สถานที่ท่องเที่ยว/ธุรกิจ (OpenStreetMap) | ทุก 30 วัน |

ทำงานได้สามทาง ใช้ร่วมกันได้เพราะทุกทางเช็กรอบจากฐานข้อมูลเดียวกัน จึงไม่ดึงซ้ำก่อนถึงรอบ

- **ระหว่างที่เซิร์ฟเวอร์เปิดอยู่** เธรดเบื้องหลังตรวจทุกชั่วโมง (ครั้งแรก 30 วินาทีหลังเปิด) ปิดได้ด้วย `AUTO_REFRESH=0` ใน `.env`
- **ปุ่ม "อัปเดตตอนนี้"** ในเมนูจัดการข้อมูล สั่งดึงทันทีโดยไม่รอรอบ
- **GitHub Actions** ([.github/workflows/refresh-data.yml](.github/workflows/refresh-data.yml)) รันทุกวันแม้ไม่มีใครเปิดเซิร์ฟเวอร์ และช่วยไม่ให้ Supabase แบบฟรีถูกพัก ต้องตั้ง secret `DATABASE_URL` ใน Settings → Secrets and variables → Actions ก่อน ถ้ายังไม่ตั้งงานจะข้ามไปเฉย ๆ

รันเองจาก command line ได้เช่นกัน

```powershell
& .\.venv\Scripts\python.exe scripts\refresh_data.py                  # เฉพาะชุดที่ถึงรอบ
& .\.venv\Scripts\python.exe scripts\refresh_data.py --only weather --force
```

ชุดที่ดึงไม่สำเร็จจะถูกลองใหม่ในรอบตรวจถัดไป และขึ้นป้าย "ดึงไม่สำเร็จ" ในเมนูจัดการข้อมูล เซิร์ฟเวอร์ Overpass สาธารณะตอบช้าหรือ timeout เป็นช่วง ๆ เป็นเรื่องปกติ
ไฟล์ CSV ของเมืองพัทยาไม่ได้อัปเดตอัตโนมัติ ต้องดาวน์โหลดแล้วนำเข้าเอง

### นำเข้าด้วยสคริปต์

สคริปต์ทุกตัวเขียนลง Supabase ตาม `DATABASE_URL` ใน `.env` และบันทึกประวัติการนำเข้าลงตาราง `imports`
ถ้าไฟล์ CSV นำเข้าไม่สำเร็จ ข้อมูลเดิมของไฟล์นั้นจะยังอยู่ครบ (ทำใน transaction ย่อยต่อไฟล์)

ไฟล์ CSV ของเมืองพัทยาดาวน์โหลดได้จาก [data.pattaya.go.th](https://data.pattaya.go.th) หรือผ่าน CKAN API เช่น
`https://data.pattaya.go.th/api/3/action/package_show?id=112`

```powershell
$env:PYTHONIOENCODING="utf-8"

# นักท่องเที่ยว (172) และประชากรแฝง (238)
& .\.venv\Scripts\python.exe scripts\import_csv.py "172-.csv" "238-.csv"

# ปริมาณรถรายแยก (112) แล้วหาพิกัดของแยก
& .\.venv\Scripts\python.exe scripts\import_csv.py "traffic_2567.csv" "traffic_2568.csv"
& .\.venv\Scripts\python.exe scripts\geocode_intersections.py

# วันหยุดและเทศกาล (ค่าเริ่มต้นใช้ปฏิทินวันหยุดไทยแบบ iCalendar ชื่อไทยทางการมาในตัว)
& .\.venv\Scripts\python.exe scripts\import_holidays.py
& .\.venv\Scripts\python.exe scripts\import_holidays.py --source world     # แหล่งสำรอง
& .\.venv\Scripts\python.exe scripts\import_holidays.py --no-observances   # เอาเฉพาะวันหยุดราชการ
```

### วิธีเลือกแบบจำลอง

ข้อมูลมีแค่ 48 เดือน และรูปแบบฤดูกาลยังไม่คงที่ (ปี 2022 เดือนพีคสูงกว่าค่าเฉลี่ยทั้งปี 69% แต่ปี 2025 เหลือ 18%
เพราะยังฟื้นตัวจากโควิด) ระบบจึงไม่ยึดวิธีใดวิธีหนึ่งไว้ล่วงหน้า แต่เทียบ 8 วิธีแล้วเลือกอัตโนมัติ
เป็นวิธีทางสถิติ 6 วิธี และวิธีที่ใช้ Machine Learning 2 วิธี ทุกวิธีแข่งด้วยกติกาเดียวกัน

1. **เลือกวิธี** จากความแม่นในปีตรวจสอบ (2024) โดยฝึกด้วยข้อมูลปี 2022–2023
2. **รายงานความแม่น** จากปีทดสอบ (2025) ซึ่งไม่ถูกใช้เลือกวิธี ตัวเลขที่ได้จึงไม่สวยเกินจริง
3. **พยากรณ์อนาคต** ด้วยวิธีที่ชนะ โดยใช้ข้อมูลทั้งหมด

**โมเดล ML** (`ml_forecasters` ใน [app/analytics.py](app/analytics.py)) เป็น ridge regression เขียนด้วย Python ล้วน
เรียนว่าแต่ละเดือนจะต่างจากค่าเฉลี่ย 12 เดือนก่อนหน้ากี่เท่า จากสิ่งที่รู้ล่วงหน้าได้จริง คือตำแหน่งของเดือนในรอบปีและจำนวนวันหยุดราชการของเดือนนั้น
เลือกความแรงของ regularization ด้วย leave-one-out ภายในชุดฝึก และให้น้ำหนักข้อมูลลดลงครึ่งหนึ่งทุก 12 เดือนที่ย้อนไป
เพราะฤดูกาลของช่วงฟื้นโควิดแรงผิดปกติ (การถ่วงน้ำหนักลดความคลาดเคลื่อนปีทดสอบของตัวผสมจาก 16.8% เหลือ 16.0%)
วิธีที่สองคือค่าเฉลี่ยของโมเดล ML กับค่าเฉลี่ย 12 เดือนล่าสุด

| วิธี | ปีตรวจสอบ 2024 (ใช้เลือก) | ปีทดสอบ 2025 ทายทั้งปี | ปีทดสอบ 2025 อัปเดตรายเดือน |
|---|:-:|:-:|:-:|
| **ผสม ML กับค่าเฉลี่ย 12 เดือนล่าสุด** (ถูกเลือก) | **14.4%** | **16.0%** | **10.9%** |
| Ridge regression (ML) | 14.9% | 20.1% | 12.2% |
| ค่าเฉลี่ย 12 เดือนล่าสุด | 17.5% | 13.3% | 11.0% |
| ระดับล่าสุด x ฤดูกาลครึ่งแรง | 17.6% | 12.8% | 8.7% |
| เดือนเดียวกันปีก่อน (วิธีพื้นฐาน) | 19.4% | 16.9% | 14.2% |
| Holt-Winters | 28.2% | 24.0% | 36.1% |

"ทายทั้งปี" คือทาย 12 เดือนล่วงหน้าจากสิ้นปีก่อน ส่วน "อัปเดตรายเดือน" คือเลื่อนจุดตัดไปทีละเดือนแล้วทายเดือนที่เหลือของปี
ซึ่งใกล้การใช้งานจริงที่มีข้อมูลเข้าทุกเดือน หน้าพยากรณ์แสดงตารางนี้ครบทุกวิธี และกราฟมีเส้นของวิธีสถิติที่ดีที่สุดเทียบกับวิธีหลัก

ผลปัจจุบัน วิธีที่ถูกเลือกคือ **ผสม ML กับค่าเฉลี่ย 12 เดือนล่าสุด** เพราะแม่นที่สุดในปีตรวจสอบ
คลาดเคลื่อนในปีทดสอบ **16.0%** เมื่อทายทั้งปี ดีกว่าวิธีพื้นฐาน (16.9%) และ **10.9%** เมื่ออัปเดตรายเดือน

**ต้องบอกตรง ๆ ว่าวิธีที่ถูกเลือกไม่ใช่วิธีที่ดีที่สุดในปีทดสอบ** วิธีสถิติง่าย ๆ สองวิธีทายทั้งปีได้แม่นกว่า (13.3% และ 12.8%)
และก่อนเพิ่ม ML ระบบเลือกค่าเฉลี่ย 12 เดือนล่าสุดซึ่งคลาดเคลื่อน 13.3% โมเดล ML เรียนฤดูกาลที่แรงของปี 2022–2024
แต่ปี 2025 ฤดูกาลอ่อนลง จึงทายสูงเกินในครึ่งปีแรก ระบบไม่สลับไปใช้วิธีที่ชนะปีทดสอบ เพราะจะเท่ากับเลือกวิธีจากข้อสอบที่ใช้วัดผล

**การเลือกวิธียังไม่นิ่ง และแก้ด้วยการวัดถี่ขึ้นไม่ได้** เคยทดลองเปลี่ยนไปเลือกจากการวัดแบบเลื่อนจุดตัดตลอดปีตรวจสอบ (78 การทายแทน 12)
วิธีที่ชนะกลายเป็น "เดือนเดียวกันปีก่อน" ซึ่งแพ้เกือบทุกวิธีในปีทดสอบ และให้ช่วงประมาณกว้างจนใช้วางแผนไม่ได้ จึงไม่ได้ใช้กติกานั้น
การทายทั้ง 78 ครั้งมาจากปีเดียวกัน ความผิดพลาดจึงไปทางเดียวกัน ปัญหาจริงคือมีปีตรวจสอบปีเดียว ต้องมีข้อมูลหลายปีกว่านี้จึงจะบอกได้ว่าวิธีไหนดีกว่าจริง

ช่วงประมาณ 95% คำนวณจากความคลาดเคลื่อนจริงของการทายล่วงหน้า 1 เดือน แล้วขยายตาม √(เดือนข้างหน้า)
พยากรณ์รายได้ในหน้า "ธุรกิจของฉัน" ยังใช้เฉพาะวิธีทางสถิติ 6 วิธี

### ผลกระทบของฝนและวันหยุด

ตัดฤดูกาล (ratio-to-moving-average) และแนวโน้มเชิงเส้นออกจากจำนวนนักท่องเที่ยวก่อน เหลือเป็นดัชนี 1.0 = เท่าที่ควรจะเป็น
เพื่อไม่ให้ "ฝนตกช่วงโลว์ซีซัน" ถูกนับซ้ำเป็นผลของฝน แล้ววัดความสัมพันธ์กับฝนที่มากกว่าปกติของเดือนนั้น

| ปัจจัย | ผล | ข้อมูลที่ใช้ |
|---|---|---|
| ฝนมากกว่าปกติ 100 มม. | นักท่องเที่ยว **-17.3%** (r = -0.37, ช่วงความเชื่อมั่น -0.59 ถึง -0.09) ชัดเจนพอที่จะไม่ใช่ความบังเอิญ | 48 เดือน |
| วันหยุดราชการเพิ่ม 1 วัน | +1.75% (r = 0.17, ช่วงความเชื่อมั่น -0.12 ถึง 0.44 คร่อมศูนย์) **ยังสรุปไม่ได้** | 48 เดือน |
| PM2.5 สูงกว่าปกติ 10 มคก./ลบ.ม. | +31.3% (r = 0.50, ช่วงความเชื่อมั่น -0.15 ถึง 0.84 คร่อมศูนย์) **ยังสรุปไม่ได้** | 24 เดือน (สองปี) |

PM2.5 มีข้อมูลแค่ปี 2024–2025 และปี 2024 ฝุ่นสูงกว่าปี 2025 ทุกเดือน ขณะที่นักท่องเที่ยวปี 2024 ก็มากกว่าด้วย
ถ้าวัดแบบเดียวกับฝนจะได้ r = 0.69 ที่ดูชัดเจน แต่จริง ๆ เป็นแค่ความต่างระหว่างสองปี จึงหักระดับของทั้งปีออกก่อน
และคิดช่วงความเชื่อมั่นจากจุดที่เป็นอิสระต่อกันจริง 11 จุด (ดู `pm25_impact` ใน [app/analytics.py](app/analytics.py))

### ข้อจำกัดที่ต้องบอกเวลานำเสนอ

- เป็นความสัมพันธ์ ไม่ใช่การพิสูจน์เหตุและผล
- ข้อมูลนักท่องเที่ยวเป็นรายเดือน จึงดูผลของฝนรายวันหรือวันหยุดแต่ละวันไม่ได้
- วัดผลของวันหยุดได้ครบ 48 เดือนแล้วหลังเปลี่ยนแหล่งข้อมูล (เดิมมีแค่ 24 เดือน) แต่ผลยังไม่ชัดเจนพอจะสรุป ต่างจากผลของฝนที่ชัดเจน
- คำแนะนำเรื่องกำลังคนและสต็อกตั้งอยู่บนสมมติฐานว่าแปรผันตรงกับจำนวนนักท่องเที่ยว เพราะฐานข้อมูลไม่มีข้อมูลร้านค้า พนักงาน หรือยอดขาย สมมติฐานนี้เขียนกำกับไว้ในคำแนะนำทุกข้อบนแดชบอร์ด
- ข้อมูลนักท่องเที่ยวล่าสุดคือเดือน 2025-12 ถ้าช้ากว่าปัจจุบันเกิน 2 เดือน แดชบอร์ดจะเตือนให้นำเข้าข้อมูลใหม่

## พฤติกรรมการเดินทางและเศรษฐกิจ

หน้า **พฤติกรรมการเดินทาง** อ่านพฤติกรรมของนักท่องเที่ยวเกาะล้านจากยอดรวมรายเดือน สามมุม:
เดินทางช่วงไหนของปี (ดัชนีฤดูกาล) ขึ้นเกาะและกลับที่ท่าไหน (แยกจากชื่อเส้นทาง "ต้นทาง-ปลายทาง") และเลือกเรือประเภทใด
ข้อค้นพบเขียนเป็นประโยคโดยกฎในโค้ด ไม่ใช่ AI

ข้อจำกัดที่ต้องบอก: เป็นพฤติกรรม**ระดับกลุ่ม** ไม่ได้ติดตามนักท่องเที่ยวรายคน และส่วนต่างระหว่างขาไปกับขากลับ
(ขากลับมากกว่าราว 30%) อธิบายได้สองทางที่ข้อมูลแยกไม่ได้ คือคนที่ไปด้วยเรือเช่าเหมาลำแล้วกลับด้วยเรือโดยสาร หรือการบันทึกสองขาไม่ครบเท่ากัน

หน้า **เศรษฐกิจและประชากร** แสดงรายได้ของเทศบาลเมืองพัทยารายปีงบประมาณ แยกหมวด เป็นข้อมูลเศรษฐกิจชุดเดียวที่เมืองเผยแพร่
**ไม่ใช่รายได้จากการท่องเที่ยว** และเป็นรายปี จึงเทียบกับจำนวนนักท่องเที่ยวรายเดือนไม่ได้ ไฟล์ต้นทางมีรหัสรายการซ้ำกันบางรายการ
และภาษีป้ายปีงบ 2565 กับ 2566 เป็นตัวเลขเดียวกันทุกหลัก ซึ่งน่าจะเป็นการกรอกซ้ำ

## ธุรกิจของฉัน

หน้าสำหรับผู้ประกอบการ อัปโหลดรายได้รายเดือนของธุรกิจตัวเอง แล้วระบบวางเทียบกับบริบทของเมือง
(นักท่องเที่ยว ฝน วันหยุด) ด้วยวิธีเดียวกับการวิเคราะห์ผลกระทบของเมือง พร้อมพยากรณ์รายได้ 3 เดือนและคำแนะนำจากตัวเลขของธุรกิจเอง

**รูปแบบไฟล์** CSV รายเดือน ดาวน์โหลดแม่แบบได้จากหน้าเว็บ ([static/business-template.csv](static/business-template.csv))

```
year,month,revenue,customers
2565,1,1250000.50,640
2565,2,1180000,598
```

| คอลัมน์ | ความหมาย | หมายเหตุ |
|---|---|---|
| `year` (หรือ `calendar_year`) | ปี | พ.ศ. หรือ ค.ศ. ก็ได้ |
| `month` (หรือ `month_id`) | เดือน 1–12 | |
| `revenue` (หรือ `revenue_baht`) | รายได้ของเดือนนั้น หน่วยบาท | ใส่จุลภาคคั่นหลักได้ถ้าครอบด้วยเครื่องหมายคำพูด |
| `customers` (หรือ `guests`) | จำนวนลูกค้าหรือคืนที่ขาย | ไม่ใส่ก็ได้ ถ้าใส่ต้องใส่ทุกเดือนจึงจะคำนวณรายได้ต่อลูกค้า |

- เดือนต้อง**ต่อเนื่องไม่ขาดช่วง** และไม่ซ้ำ ไฟล์ที่มีแถวผิดจะไม่ถูกบันทึกเลย พร้อมบอกเลขบรรทัด
- ต้องมี**อย่างน้อย 24 เดือน** จึงจะหาฤดูกาล ความสัมพันธ์ และพยากรณ์ได้ ถ้าจะเทียบกับนักท่องเที่ยวให้ครบ ควรอยู่ในช่วง ม.ค. 2565 – ธ.ค. 2568
- การอัปโหลดแทนที่ข้อมูลเดิมของผู้ใช้คนนั้นทั้งชุด หนึ่งผู้ใช้มีหนึ่งธุรกิจ

**ความเป็นส่วนตัว** ทุกคำขออ่านเฉพาะข้อมูลของผู้ใช้ที่ล็อกอินอยู่ ไม่มี endpoint ให้ดูของคนอื่น แม้เป็นผู้ดูแลระบบ
ประวัติการใช้งานบันทึกแค่ว่ามีการอัปโหลดกี่เดือน ไม่บันทึกตัวเลข และข้อมูลลบตามเมื่อผู้ใช้ถูกลบ

**AI ของธุรกิจ** ปุ่ม "ให้ AI สรุปและจัดลำดับ" ทำแบบเดียวกับของเมือง คือเรียบเรียงบทสรุปและจัดลำดับคำแนะนำที่กฎสร้างไว้ (`POST /api/business/ai`)
ข้อมูลออกนอกระบบเฉพาะเมื่อเจ้าของกดปุ่มเอง ถ้าไม่ได้ติ๊กว่าเป็นข้อมูลสมมติจะมีกล่องให้ยืนยันก่อน เพราะโควตาฟรีของ Gemini
อนุญาตให้ Google นำข้อความไปปรับปรุงผลิตภัณฑ์ สิ่งที่ส่งคือตัวเลขสรุป (ยอดรวม พยากรณ์ ผลทางสถิติ) ไม่ใช่ตารางรายเดือนทั้งชุด
ถ้าจะใช้กับธุรกิจจริงควรเปลี่ยนเป็นบริการ AI แบบเสียเงินที่ไม่นำข้อมูลไปใช้ ผลของ AI ถูกลบเมื่ออัปโหลดข้อมูลชุดใหม่

**ข้อมูลสมมติ** ถ้าติ๊ก "เป็นข้อมูลสมมติเพื่อสาธิต" ตอนอัปโหลด ทุกกราฟในหน้านี้และหัวข้อในรายงาน PDF จะมีป้ายกำกับ
ความสัมพันธ์ที่เห็นจากข้อมูลสมมติคือสิ่งที่ผู้สร้างข้อมูลใส่เข้าไป ใช้แสดงว่าระบบทำงานอย่างไร ไม่ใช่ข้อค้นพบ

## บทสรุปโดย AI

AI ทำสองอย่างในคำขอเดียว ใช้ Gemini API ซึ่งมีโควตาฟรี

1. **เรียบเรียงบทสรุปผู้บริหาร** จากตัวเลขที่ระบบคำนวณไว้แล้ว แสดงบนหน้าภาพรวมและในรายงาน PDF
2. **จัดลำดับความเร่งด่วนของคำแนะนำ** เลือกไม่เกิน 6 ข้อจากคำแนะนำที่กฎของระบบสร้างไว้ พร้อมเหตุผลของแต่ละลำดับ
   AI เลือกได้เฉพาะจากรายการที่มี (จับคู่ด้วย `key` ของกฎ) แต่งคำแนะนำใหม่ไม่ได้ key ที่ไม่มีในรายการถูกทิ้ง

ตัวพยากรณ์เป็นคนละส่วนกัน ใช้โมเดล Machine Learning ที่แข่งกับวิธีทางสถิติ (ดูหัวข้อวิธีเลือกแบบจำลอง) Gemini ไม่ได้เป็นตัวพยากรณ์
ถ้าไม่ตั้งค่าหรือ AI ล่ม ระบบส่วนอื่นทำงานตามปกติ คำแนะนำจะเรียงตามลำดับของกฎเหมือนเดิม
ถ้ารุ่นหลักตอบว่าเซิร์ฟเวอร์หนาแน่น (503) ระบบจะลองรุ่นสำรอง `gemini-3.5-flash-lite` ให้เอง

**เปิดใช้:** ขอ API key ฟรีที่ [aistudio.google.com/apikey](https://aistudio.google.com/apikey) แล้วเพิ่มใน `.env`

```
GEMINI_API_KEY=<key ที่ได้>
GEMINI_MODEL=gemini-3.5-flash   # ไม่ใส่ก็ได้ ใช้ค่านี้เป็นค่าเริ่มต้น
```

เปิดเซิร์ฟเวอร์ใหม่ แล้วผู้ดูแลกดปุ่ม **สรุปใหม่** ในหน้าภาพรวม

- **AI ไม่คำนวณเอง** ระบบส่งข้อเท็จจริงที่จัดรูปแบบตัวเลขแล้ว (ดู `summary_facts` ใน [app/main.py](app/main.py)) และสั่งให้คัดลอกตัวเลขตรง ๆ ไม่สรุปเกินผลสถิติ (กติกาอยู่ใน [app/ai_summary.py](app/ai_summary.py))
- **ตรวจตัวเลขหลังได้คำตอบ** ตัวเลขในบทสรุปที่ไม่มีในข้อเท็จจริงที่ส่งไปจะขึ้นเตือนให้ผู้ดูแลเห็น เป็นการตรวจเฉพาะตัวเลข ไม่ได้ตรวจความถูกต้องของประโยค ผู้ดูแลควรอ่านก่อนเผยแพร่
- **เรียก AI เฉพาะตอนกดปุ่ม** บทสรุปเก็บในตาราง `ai_summaries` พร้อมข้อเท็จจริงที่ส่งไป เปิดหน้าเว็บกี่ครั้งก็ไม่กินโควตา ถ้ามีข้อมูลนำเข้าใหม่หลังสรุป จะขึ้นข้อความบอก
- **โควตาฟรีมีเงื่อนไข** ข้อความที่ส่งผ่านโควตาฟรีถูก Google นำไปใช้ปรับปรุงผลิตภัณฑ์ได้ ข้อมูลที่ส่งเป็นสถิติรวมจาก Open Data จึงไม่มีข้อมูลส่วนบุคคล เพดานการใช้ดูได้ในหน้า rate limit ของ AI Studio

## ผู้ใช้งานและสิทธิ์ (RBAC)

ทุก endpoint ที่คืนข้อมูลต้องเข้าสู่ระบบก่อน ผู้ที่ยังไม่ล็อกอินจะได้ `401` และหน้าเว็บจะแสดงหน้าเข้าสู่ระบบแทนแดชบอร์ด
ผู้ที่ล็อกอินแล้วแต่บทบาทไม่มีสิทธิ์จะได้ `403` และหน้าเว็บจะซ่อนส่วนนั้นไปเลย

| สิทธิ์ | ครอบคลุม | ผู้ดูแลระบบ | ผู้บริหาร | ผู้ประกอบการ |
|---|---|:-:|:-:|:-:|
| `view:overview` | KPI นักท่องเที่ยว อากาศ วันหยุด | ✓ | ✓ | ✓ |
| `view:spatial` | แผนที่ แยกจราจร ย่าน สถานที่ | ✓ | ✓ | ✓ |
| `view:forecast` | พยากรณ์และผลกระทบฝน/วันหยุด | ✓ | ✓ | ✓ |
| `view:recommendations` | ข้อเสนอแนะเชิงกลยุทธ์ | ✓ | ✓ | ✓ |
| `export:report` | ออกรายงานผู้บริหาร | ✓ | ✓ | ✓ |
| `view:demographics` | ประชากรแฝง | ✓ | ✓ | — |
| `view:sources` | แหล่งข้อมูลและประวัติการนำเข้า | ✓ | ✓ | — |
| `manage:users` | จัดการผู้ใช้ บทบาท และประวัติการใช้งาน | ✓ | — | — |
| `manage:data` | นำเข้าไฟล์ข้อมูล และสั่งอัปเดตข้อมูลจาก API | ✓ | — | — |
| `manage:business` | อัปโหลดและดูผลวิเคราะห์ธุรกิจของตัวเอง | ✓ | — | ✓ |

ผู้ประกอบการไม่เห็นประชากรแฝงเพราะเป็นข้อมูลระดับนโยบายเมือง และไม่เห็นประวัติการนำเข้าเพราะเป็นงานดูแลระบบ

### กลไก

- รหัสผ่านเข้ารหัสด้วย `hashlib.scrypt` (n=2^14) เทียบแบบเวลาคงที่ด้วย `hmac.compare_digest`
- session เก็บใน `user_sessions` โดยเก็บเฉพาะ SHA-256 ของ token ไม่เก็บตัวจริง อายุ 12 ชั่วโมง
- คุกกี้เป็น `HttpOnly` + `SameSite=Lax` ตั้ง `COOKIE_SECURE=1` ใน `.env` เมื่อขึ้นใช้งานจริงผ่าน HTTPS
- ข้อความตอบตอนล็อกอินผิดเหมือนกันทั้งกรณีชื่อผู้ใช้ผิดและรหัสผ่านผิด เพื่อไม่ให้ไล่เดาว่ามีชื่อผู้ใช้นั้นอยู่จริงหรือไม่
- ลบผู้ใช้หรือเปลี่ยนรหัสผ่านจะลบ session ที่ค้างอยู่ด้วย คนที่ถือคุกกี้เดิมใช้ต่อไม่ได้
- ระบบไม่ยอมให้ลบบัญชีตัวเอง และต้องเหลือผู้ดูแลระบบอย่างน้อยหนึ่งคนเสมอ
- `audit_logs` บันทึกการเข้า/ออกระบบ การล็อกอินไม่สำเร็จ การเพิ่ม/ลบผู้ใช้ การนำเข้าไฟล์ และการอัปเดตข้อมูลอัตโนมัติ (ผู้กระทำ `system`)

### สมัครสมาชิกเอง (รออนุมัติ)

หน้าเข้าสู่ระบบมีลิงก์ **สมัครสมาชิก** ให้ผู้ประกอบการหรือผู้บริหารยื่นคำขอเองได้
บัญชีที่สมัครจะอยู่ในสถานะ `pending` **เข้าสู่ระบบไม่ได้** จนกว่าผู้ดูแลระบบจะกดอนุมัติในแผงจัดการผู้ใช้
ซึ่งเป็นจุดที่ผู้ดูแลกำหนดบทบาทจริงให้ (จะให้ตามที่ขอมาหรือไม่ก็ได้)

| สถานะ | ความหมาย |
|---|---|
| `pending` | สมัครแล้วรออนุมัติ ล็อกอินได้แต่ถูกปฏิเสธด้วย `403` พร้อมข้อความว่ารออนุมัติ |
| `active` | ใช้งานได้ตามบทบาทที่ได้รับ |
| `rejected` | ถูกปฏิเสธหรือระงับ เก็บแถวไว้เป็นหลักฐานแทนการลบทิ้ง และ session ที่ค้างถูกตัดทันที |

ข้อควรรู้ด้านความปลอดภัยของหน้าสมัคร

- **เลือกบทบาทเองได้เฉพาะผู้บริหารและผู้ประกอบการ** ไม่มีทางสมัครเป็นผู้ดูแลระบบได้ และบทบาทที่ขอมาเป็นเพียงคำขอ ผู้ดูแลเป็นคนตัดสินใจขั้นสุดท้าย
- **สมัครด้วยชื่อผู้ใช้ที่มีอยู่แล้วจะได้คำตอบเหมือนสมัครสำเร็จ** เพื่อไม่ให้คนนอกใช้หน้าสมัครไล่เช็กว่ามีชื่อผู้ใช้ใดอยู่ในระบบบ้าง (ผู้ดูแลจะเห็นในประวัติว่าเป็นคำขอซ้ำ)
- **จำกัดการสมัคร 5 ครั้งต่อชั่วโมงต่อ IP** นับเฉพาะคำขอที่กรอกข้อมูลถูกต้องแล้ว คำขอที่กรอกผิดจึงไม่กินโควตา ตัวนับเก็บในหน่วยความจำของโปรเซส ถ้าขึ้นใช้งานจริงหลายเครื่องต้องย้ายไปเก็บที่ส่วนกลาง
- ชื่อผู้ใช้รับเฉพาะตัวอักษรอังกฤษ ตัวเลข `_` และ `.` อย่างน้อย 3 ตัว ส่วนหน่วยงานรับภาษาไทยได้
- หน้าสมัครเก็บเฉพาะชื่อผู้ใช้ หน่วยงาน รหัสผ่าน และบทบาทที่ขอ ไม่เก็บชื่อ-นามสกุลและอีเมล เพราะเป็นต้นแบบสำหรับทดลองระบบ ยังไม่มีการยืนยันตัวตนทางอีเมล (คอลัมน์ `full_name` และ `email` ยังอยู่ในตาราง ผู้ดูแลกรอกให้ได้ตอนสร้างผู้ใช้เอง)

### ผู้ดูแลระบบคนแรก

ครั้งแรกที่เปิดเซิร์ฟเวอร์ ถ้ายังไม่มีผู้ใช้เลย ระบบจะสร้างบัญชี `admin` ให้อัตโนมัติ แล้วพิมพ์รหัสผ่านที่สุ่มให้
ออกทาง console **ครั้งเดียว** ตั้งเองล่วงหน้าได้ด้วย `ADMIN_USERNAME` และ `ADMIN_PASSWORD` ใน `.env`

### จัดการผู้ใช้จาก command line

ใช้ตอนลืมรหัสผ่านจนเข้าหน้าเว็บไม่ได้

```powershell
& .\.venv\Scripts\python.exe scripts\manage_users.py list
& .\.venv\Scripts\python.exe scripts\manage_users.py create somchai executive --full-name "สมชาย ใจดี"
& .\.venv\Scripts\python.exe scripts\manage_users.py reset admin
& .\.venv\Scripts\python.exe scripts\manage_users.py set-role somchai operator
& .\.venv\Scripts\python.exe scripts\manage_users.py delete somchai
```

## การแบ่งย่าน (Micro-Zoning)

ชุดข้อมูลปริมาณรถบอกได้แค่ระดับ "แยก" และ POI บอกได้แค่ระดับ "จุด" ซึ่งยังตอบไม่ได้ว่าคนกระจุกอยู่ย่านไหน
`MICRO_ZONES` ใน [app/main.py](app/main.py) จึงนิยามย่านท่องเที่ยวหลัก 8 ย่านเป็นจุดศูนย์กลางกับรัศมี
แล้วนับ POI และแยกเข้าย่านที่ศูนย์กลางใกล้ที่สุด (วัดระยะด้วยสูตร haversine) จุดหนึ่งจุดถูกนับให้ย่านเดียวเสมอ จึงไม่มีการนับซ้ำ

| ย่าน | รัศมี | ธุรกิจ | ความหนาแน่น (แห่ง/ตร.กม.) | ประเภทเด่น |
|---|---|---|---|---|
| พัทยากลาง | 1.4 กม. | 1,350 (45.4%) | 219.2 | bar |
| หาดจอมเทียน | 2.2 กม. | 389 (13.1%) | 25.6 | bar |
| พัทยาตะวันออก (สุขุมวิท) | 3.0 กม. | 365 (12.3%) | 12.9 | restaurant |
| พัทยาใต้ / วอล์กกิ้งสตรีท | 1.2 กม. | 221 (7.4%) | 48.9 | restaurant |
| พัทยาเหนือ | 1.4 กม. | 214 (7.2%) | 34.8 | restaurant |
| เขาพระตำหนัก | 1.3 กม. | 197 (6.6%) | 37.1 | restaurant |
| นาเกลือ | 1.6 กม. | 37 (1.2%) | 4.6 | restaurant |
| เกาะล้าน | 2.5 กม. | 0 | 0.0 | — |

ธุรกิจ 93.2% ตกอยู่ในย่านที่กำหนด ที่เหลือ 6.8% อยู่นอกทุกย่าน

**ข้อจำกัดที่ต้องบอกเวลานำเสนอ**

- ขอบเขตย่านเป็นวงกลมโดยประมาณจากพิกัด OpenStreetMap ไม่ใช่ขอบเขตการปกครองตามกฎหมาย
- ความหนาแน่นคิดจากพื้นที่วงกลมเต็มวง ย่านที่มีทะเลอยู่ในวง (จอมเทียน เกาะล้าน) จะได้ค่าต่ำกว่าความจริง
- **เกาะล้านได้ 0 แห่ง** เพราะการดึง POI จาก OpenStreetMap ครอบคลุมเฉพาะฝั่งแผ่นดิน ทั้งที่ข้อมูลนักท่องเที่ยวที่ใช้ทั้งระบบเป็นข้อมูลผู้เดินทางลงเกาะล้าน ถ้าจะวิเคราะห์เกาะล้านต่อ ต้องขยายขอบเขตตอนดึง POI ก่อน
- แยกที่ไม่มีพิกัด 13 แยก และแยกที่อยู่นอกย่าน ไม่ถูกนับให้ย่านใด ปริมาณรถรายย่านจึงต่ำกว่ายอดรวมทั้งเมือง

## รายงานผู้บริหาร

ปุ่ม **ออกรายงานผู้บริหาร (PDF)** บนแดชบอร์ดสร้างรายงานจัดรูปแบบ A4 แล้วเรียกหน้าต่างพิมพ์ของเบราว์เซอร์
(เลือก "Save as PDF" เพื่อบันทึกเป็นไฟล์) รายงานประกอบด้วย KPI ภาพรวม ตารางรายย่อย ตารางพยากรณ์ 6 เดือน
ผลของฝนและวันหยุด ข้อเสนอแนะ ตารางแหล่งข้อมูล และข้อจำกัดทุกข้อของทุกส่วน

รายงานสร้างจาก DOM ที่ซ่อนไว้ในหน้าเดิม (`#print-report` + `@media print`) ไม่ได้เปิดหน้าต่างใหม่
เพราะตัวบล็อกป๊อปอัปของเบราว์เซอร์มักบล็อกหน้าต่างที่สคริปต์เปิดเอง กราฟฝังเป็นรูปจาก canvas ของ Chart.js โดยตรง

## พิกัดของแยก

ชุดข้อมูลปริมาณรถไม่มีพิกัดมาให้ `geocode_intersections.py` จึงหาพิกัดจาก OpenStreetMap สองวิธี
และบันทึกวิธีที่ใช้ไว้ในคอลัมน์ `geocode_method` เพื่อให้ตรวจสอบย้อนกลับได้

| วิธี | ความหมาย | ครอบคลุม |
|---|---|---|
| `osm_junction_name` | โหนดแยกใน OSM ที่มีแท็ก `name` ตรงกับชื่อแยก (แม่นที่สุด) | 9 แยก |
| `osm_road_pair` | จุดที่ถนนสองสายตัดกันจริงใน OSM เช่น "แยกพัทยากลาง" = ถนนพัทยากลาง × ถนนสุขุมวิท | 20 แยก |
| `NULL` | OSM ไม่มีทั้งชื่อแยกและชื่อถนนที่ระบุได้ จึงไม่ใส่พิกัด | 13 แยก |

รวม **29 จาก 42 แยกมีพิกัด** แยกที่ยังไม่มีพิกัดจะไม่ขึ้นบนแผนที่ แต่ยังมีข้อมูลปริมาณรถใช้ดูอันดับและกราฟได้ตามปกติ

- ชุดข้อมูลนักท่องเที่ยวครอบคลุมเฉพาะผู้เดินทางลงเกาะล้าน ไม่ใช่นักท่องเที่ยวทั้งเมืองพัทยา
- แหล่งวันหยุดหลักให้ชื่อไทยทางการมาในตัว ส่วนแหล่งสำรอง (`--source world`) ให้ชื่ออังกฤษเท่านั้น ชื่อไทยจึงมาจากตาราง `THAI_NAMES` ใน `scripts/import_holidays.py`
- ตาราง `public_holidays` เก็บทั้งวันหยุดราชการ (`public`/`observed`) และวันสำคัญที่ราชการไม่ได้หยุด (`observance` เช่น ตรุษจีน คริสต์มาส) การนับ "จำนวนวันหยุดต่อเดือน" ในการวิเคราะห์นับเฉพาะสองประเภทแรก
- รหัสผ่านเข้ารหัสด้วย scrypt ของไลบรารีมาตรฐาน ไม่ได้เพิ่มไลบรารีภายนอก
